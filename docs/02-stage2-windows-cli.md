# Етап 2. CLI-прототип для Windows

Дата: 2026-10-24. Статус: **код готовий, чекає перевірки на реальній Windows-машині.**

## Що зроблено

**`recorder-core`** — спільне ядро без залежностей від ОС:

- **Часова шкала.** Кожне джерело (мікрофон, системний звук) прив'язане до монотонного годинника ОС (QPC). Ресемплінг у 16 кГц робить `rubato` (sinc). Дрейф годинників компенсує PI-регулятор, який підкручує коефіцієнт ресемплінгу не більш як на ±0,5 %.
- **Діри заповнюються тишею автоматично.** Коли WASAPI loopback мовчить, коли пристрій перепідключається або мікрофон довго відкривається, записувач бере тишу. Він кодує звук із запізненням 400 мс від «зараз», тож усе, що встигли захопити, вже лежить на шкалі.
- **Формат:** Opus multistream (2 незалежні моно-потоки, mapping family 1, VOIP, VBR 32 кбіт/с, фрейм 20 мс) в Ogg.
- **Збереження:** сторінка Ogg закривається щосекунди, після чого `fsync`.
- **Частини змінюються рівно кожні 30 000 фреймів (10 хв).** Останній пакет частини несе перший фрейм наступної, а granule position обрізає зайве. Тому на межах немає ні втрат, ні дублікатів.
- **`manifest.json`:** усі поля з ТЗ плюс журнал подій пристроїв. Записується атомарно (tmp → fsync → rename).
- **Відновлення після збою:** сесії зі статусом `recording`, чий lock-файл не тримає живий процес, закриваються. Недописана сторінка обрізається, тривалості перераховуються з файлів, статус стає `crashed_recovered`. Запускається автоматично при `recorder start` і окремо через `recorder recover`.
- **Вбудований декодер** для `recorder verify`, щоб перевіряти записи без ffmpeg.

**`recorder-capture`**:

- **Мікрофон через `cpal`.** Слідує за пристроєм за замовчуванням: раз на секунду перевіряє, чи не змінився він, і перевідкриває потік після фатальних помилок (з back-off).
- **WASAPI loopback:**
  - працює за подіями, а не опитуванням;
  - за кожне пробудження читає всі пакети;
  - буфер із прапорцем `SILENT` записується як нулі;
  - кожен буфер має QPC-мітку часу;
  - стежить за пристроєм виводу за замовчуванням;
  - режим `--process Zoom.exe` пише лише звук цієї програми та її дочірніх процесів.
- **Тип виводу** (колонки чи навушники) визначається автоматично і записується в manifest як `echo_risk`.

**`recorder` (CLI):**

- команди `start`, `devices`, `recover`, `verify [--wav]`;
- рядок стану з індикаторами рівня обох каналів;
- попередження, якщо системний звук мовчить 2 хв, а мікрофон працює;
- лог-файл із щохвилинною статистикою: дрейф (ppm), розбіжність (мс), вставлена тиша, CPU (%), RAM (МБ).

**CI** (`.github/workflows/ci.yml`): fmt, clippy, тести і збірка на `windows-latest` і `macos-latest`. Артефакт — `recorder.exe`.

**CI на GitHub** ([перший запуск](https://github.com/HryhoriiHaponiukQuitCode/meeting-recorder-lite/actions/runs/40092512942)): fmt, clippy і всі тести пройшли на `windows-latest` і `macos-latest`. `recorder.exe` залежить лише від системних DLL Windows (kernel32, ole32, mmdevapi тощо), без `VCRUNTIME140.dll`, тож VC++ Redistributable не потрібен.

**Не перевірено** — і це потрібно від вас:
- реальний WASAPI loopback;
- запуск `.exe` на справжній Windows-машині.

## Відхилення від плану етапу 1

- Кодування й запис на диск виконуються в одному потоці, а не у двох. Між колбеками і цим потоком лежить кільцевий буфер на 4 с, тож повільний `fsync` колбеки не блокує. Окремий IO-потік додам, якщо логи покажуть, що `fsync` займає > 100 мс.

## Як протестувати на Windows

### 1. Отримати `recorder.exe`

**Варіант А (рекомендую).** Завантажити зібраний CI файл: [meeting-recorder-lite → Actions](https://github.com/HryhoriiHaponiukQuitCode/meeting-recorder-lite/actions) → останній зелений запуск → Artifacts → `recorder-windows-x64` (zip з `recorder.exe`, ~1,4 МБ). Або з консолі:

   ```powershell
   gh run download --repo HryhoriiHaponiukQuitCode/meeting-recorder-lite --name recorder-windows-x64
   ```

**Варіант Б.** Зібрати локально:
1. Встановити Rust: https://rustup.rs (`rustup-init.exe`, усе за замовчуванням).
2. Встановити Visual Studio Build Tools 2022 з навантаженням «Desktop development with C++». Воно включає MSVC і CMake.
3. У «Developer PowerShell for VS 2022»:

   ```powershell
   cd <папка репозиторію>
   cargo build --release -p recorder-cli
   ```

   Готовий файл: `target\release\recorder.exe`.

### 2. Сценарії перевірки

Запускайте з Windows Terminal або PowerShell.

| # | Сценарій | Що зробити | Що має бути |
|---|---|---|---|
| 1 | Пристрої | `.\recorder.exe devices` | Ваші мікрофони й пристрої виводу; тип виводу за замовчуванням |
| 2 | Базовий запис, 2 хв | `.\recorder.exe start`, увімкнути YouTube і говорити, потім Ctrl+C. Далі `.\recorder.exe verify "<шлях з виводу>" --wav` | Обидва індикатори рухаються; `verify`: усі частини OK, L і R вище −60 dBFS; у `me.wav` ваш голос, у `them.wav` відео |
| 3 | Тиша в системі | `start`, 1 хв нічого не грає, потім 30 с відео | Правий канал: тиша, потім звук **у правильний момент** (порівняйте з `me.wav` у будь-якому редакторі, наприклад Audacity) |
| 4 | Справжній дзвінок, ≥ 30 хв | Zoom/Meet/Teams у навушниках | `verify` OK, частини по 10 хв; у лозі рядки `process stats` (CPU, RSS) |
| 5 | Зміна пристроїв | Під час запису підключити/відключити навушники; у «Параметри звуку» перемкнути вивід за замовчуванням | Запис не падає; у manifest події `device_lost` / `device_opened`; звук продовжується |
| 6 | Аварійне завершення | Під час запису Диспетчер задач → recorder.exe → «Зняти задачу». Потім `.\recorder.exe recover` | `Відновлено: … N с`; у manifest статус `crashed_recovered`; `verify` OK |
| 7 | Лише Zoom (опційно) | `.\recorder.exe start --process Zoom.exe` під час дзвінка, паралельно грає YouTube | У правому каналі лише Zoom |
| 8 | Серверні команди з ТЗ (якщо є ffmpeg) | Команди `ffmpeg -i part_0001.ogg -af "pan=mono\|c0=c0" -ar 16000 me.wav` (і `c0=c1`) | Відпрацьовують без помилок |

### 3. Що надіслати мені

Для кожного сценарію з проблемою (і для №4 у будь-якому разі):

1. Лог: `%LOCALAPPDATA%\Meeting Recorder\logs\recorder.<дата>.log`. Для детальнішого логу запустіть з `$env:RECORDER_LOG="debug"`.
2. `manifest.json` із папки сесії.
3. Вивід `recorder verify "<папка>"`.
4. Текст помилки з консолі, якщо вона була.
5. Версію Windows і чим грали звук (навушники, колонки, Bluetooth).

Аудіофайли надсилати не обов'язково (там ваші розмови). Якщо проблема в якості звуку, достатньо короткого фрагмента.

## Відомі обмеження (наступні етапи)

- **macOS:** поки записується лише мікрофон; системний звук буде на етапі 3.
- **Ехоподавлення** для колонок: етап 4. Зараз ризик луни лише фіксується в manifest і показується попередженням.
- **Сон / гібернація:** обробки ще немає (етап 4). Якщо комп'ютер засне посеред запису, після пробудження запис продовжиться, але час сну може бути заповнено тишею.
- Індикатори в треї, нагадування про згоду з «більше не показувати»: етап 5. У CLI нагадування показується при кожному старті.
